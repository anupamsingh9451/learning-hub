3. 20 BACKEND CONCEPTS (DEEP DIVE)
------------------------------------------------------------

    01. CLIENT-SERVER ARCHITECTURE
        Kya hai : Client request bhejta hai (browser, mobile app), server
                  request process karke database se baat karta hai aur
                  response lautata hai.
        Tiers   : 2-Tier (client <-> DB/server), 3-Tier (UI <-> App Logic <-> DB),
                  Multi-Tier (Microservices, API Gateway).
        Interview: "Jab URL type karte ho toh kya hota hai?"
                  DNS resolution -> TCP Handshake (SYN, ACK) -> TLS negotiation
                  -> HTTP Request -> Backend processing -> DB query ->
                  Response render.

    02. REST APIS
        Kya hai : Representational State Transfer — networked systems ka
                  architectural pattern jisme resources URLs ke through
                  expose hote hain aur standard HTTP methods use hote hain.
        Rules   :
                  - Client-Server separation (frontend aur backend alag).
                  - Statelessness (har request me poora context hona chahiye;
                    server pichli request pe depend na kare).
                  - Cacheable responses (Cache-Control headers).
                  - Uniform interface (nouns use karo: `/api/products`, `/api/orders`).
        Interview: "HTTP aur REST me farak?" HTTP ek transport protocol hai;
                  REST ek design architectural style hai jo HTTP ko use karta hai.

    03. HTTP METHODS & STATUS CODES
        Methods :
                  - GET    : Read only (safe & idempotent).
                  - POST   : Naya resource create karna (non-idempotent).
                  - PUT    : Poora resource replace karna (idempotent).
                  - PATCH  : Partial field update karna (generally non-idempotent).
                  - DELETE : Resource remove karna (idempotent).
        Idempotency:
                  Ek hi request ko baar-baar bhejne par server ki final state
                  par wahi asar pade jo 1 baar bhejne par padta. Payments me
                  hamesha Idempotency Keys use karo.
        Codes   :
                  - 200 OK, 201 Created, 204 No Content.
                  - 400 Bad Request, 401 Unauthorized (Identity missing),
                    403 Forbidden (Permission denied), 404 Not Found,
                    409 Conflict, 422 Validation Error, 429 Rate Limited.
                  - 500 Server Error, 502 Bad Gateway, 503 Unavailable, 504 Timeout.

    04. AUTHENTICATION VS AUTHORIZATION
        AuthN   : "Who are you?" (Pehchan verify karna — email/pass, OTP, SSO).
        AuthZ   : "What can you do?" (Ijaazat check karna — admin role, ownership).
        Models  :
                  - RBAC (Role-Based Access Control): Role = Admin / User / Editor.
                  - ABAC (Attribute-Based): User ID, Department, Resource Ownership.
        Security: Server-side check mandatory hai. IDOR (Insecure Direct Object
                  References) se bacho — URL me `user_id=102` badal kar dusre ka
                  data access na ho sake.

    05. JWT VS SESSIONS
        Sessions: Stateful. Server (Redis ya DB) me session ID store hoti hai;
                  cookie me ID aati hai. Invalidation/Logout aasan hai, par
                  shared storage chahiye horizontally scaled servers par.
        JWTs    : Stateless. Token me Header + Payload + Signature hota hai.
                  Server bina DB lookup ke verify kar sakta hai.
                  Drawback: Token expire hone tak revoke karna mushkil hai;
                  payload encrypted nahi hota (sirf signed hota hai, base64 readable).
        Decision: Centralized logout/revocation chahiye = Sessions/Redis.
                  Microservices ya decoupled mobile APIs = Short-lived JWT + Refresh Tokens.

    06. API VERSIONING
        Kyun    : Naye badlav purane clients (mobile apps jo update nahi hue)
                  ko na todein.
        Types   :
                  - URL Path: `/api/v1/users` (sabse popular, simple).
                  - Query Param: `/api/users?v=2`.
                  - Header: `X-API-Version: 2`.
                  - Content Negotiation: `Accept: application/vnd.app.v2+json`.
        Rule    : Naya optional field add karne par versioning mat badlo;
                  breaking schema changes par hi v2 banao.

    07. SQL VS NOSQL
        SQL (Relational):
                  - Structured tables, foreign keys, strict schemas, ACID guarantees.
                  - Best for: Financial systems, e-commerce orders, relational data.
                  - Examples: PostgreSQL, MySQL.
        NoSQL:
                  - Document (MongoDB), Key-Value (Redis), Wide-Column (Cassandra), Graph (Neo4j).
                  - Best for: Unstructured data, dynamic schemas, caching, graphs.
        Reality : Modern systems me dono saath chalte hain (Postgres for transactions + Redis for cache).

    08. DATABASE INDEXING
        Kya hai : B-Tree ya Hash data structure jo table scan (O(N)) ko O(log N)
                  lookup me badal deta hai.
        Syntax  : `CREATE INDEX idx_users_email ON users(email);`
        Tradeoff: Read tez hoti hai, par Write (INSERT/UPDATE/DELETE) slow hoti
                  hai kyunki har write par index tree rebuild hota hai.
        Rule    : Sirf un columns par index lagao jo WHERE, JOIN, ya ORDER BY me
                  frequently use hote hain.

    09. TRANSACTIONS & ACID
        Example : Bank Transfer (Account A se paise deduct karo, Account B me add karo).
                  Dono kaam hone chahiye ya koi nahi.
        ACID    :
                  - Atomicity   : All or nothing (Rollback on failure).
                  - Consistency : Database ke rules/constraints preserve rahein.
                  - Isolation   : Concurrent transactions ek dusre ko corrupt na karein.
                  - Durability  : Commit hone ke baad power cut pe bhi data safe rahe.
        Anomalies: Dirty Read, Non-Repeatable Read, Phantom Read.

    10. DATABASE NORMALIZATION
        Kyun    : Data redundancy (duplication) aur anomalies (insert/update/delete bugs) hatana.
        Forms   :
                  - 1NF: Atomic values, repeating groups nahi.
                  - 2NF: 1NF + partial key dependency nahi.
                  - 3NF: 2NF + transitive dependency nahi (A -> B -> C).
        Denormalization:
                  Analytics aur heavy read workloads me intentionally tables ko join
                  karke duplicate data rakha jaata hai taaki runtime queries tez hon.

    11. CONNECTION POOLING
        Kyun    : Naya TCP/DB connection kholna bohot expensive hota hai.
        Solution: Pre-created connections ka pool rakho; request aane par pool se
                  connection lo, kaam khatam hone par wapas pool me daal do.
        Gotcha  : Pool size itna bada mat karo ki database crash ho jaaye. Long-running
                  external API calls ke dauran DB connection hold mat karo.

    12. THE N+1 QUERY PROBLEM
        Samasya : 100 orders lane ke liye 1 query chalayi, phir har order ke customer
                  ke liye 1-1 query chalayi (1 + 100 = 101 queries).
        Solution:
                  - SQL me `JOIN` use karo.
                  - ORM me Eager Loading use karo (Laravel: `Order::with('customer')->get()`,
                    Prisma: `include: { customer: true }`).

    13. CACHING
        Layers  : Browser -> CDN (Cloudflare) -> App Memory -> Distributed (Redis).
        Pattern : Cache-Aside (Pehle cache dekho -> hit par return -> miss par DB se
                  lao aur cache me daalo).
        Problems:
                  - Cache Invalidation: Data change hone par purani key delete karna.
                  - Cache Stampede: Key expire hote hi hazaron requests ek saath DB par girna.
                  - Cache Penetration: Aise ID ke liye bar-bar query jo DB me hai hi nahi.

    14. LOAD BALANCING
        Kya hai : Incoming traffic ko multiple backend instances ke beech baantna.
        Algos   : Round Robin, Weighted Round Robin, Least Connections, IP Hash.
        Health Checks:
                  Failing/crashed server ko rotation se turant bahar nikal dena taaki
                  users ko errors na dikhein.
        Rule    : Servers stateless hone chahiye; session ko kisi ek server ki RAM me mat rakho.

    15. HORIZONTAL VS VERTICAL SCALING
        Vertical (Scale Up)   : Badi machine lo (more CPU, more RAM). Simple hai par
                                hardware limit aur single point of failure hota hai.
        Horizontal (Scale Out): Aur machines jodo (multiple small servers + load balancer).
                                High availability milti hai par distributed complexity aati hai.

    16. MESSAGE QUEUES
        Kyun    : Heavy kaam (email bhejna, invoice PDF generate karna, video encode)
                  ko request cycle se bahar nikal kar asynchronously background me karna.
        Tools   : RabbitMQ, Apache Kafka, Amazon SQS, Redis Queues.
        Semantics: At-most-once (kho sakta hai), At-least-once (duplicate aa sakta hai ->
                  consumers ko HAMESHA Idempotent banao).
        DLQ     : Dead-Letter Queue — jo messages 3-5 baar fail ho jaayein unhe inspect
                  karne ke liye alag queue me daalna.

    17. RATE LIMITING
        Kyun    : DDoS attacks, brute force login, aur expensive API scraping rokna.
        HTTP 429: Too Many Requests + `Retry-After: 60` header.
        Algos   : Fixed Window, Sliding Window Log, Token Bucket, Leaky Bucket.
        Tool    : Redis atomic counters (`INCR` + `EXPIRE`) distributed rate limiting ke liye.

    18. RETRIES & TIMEOUTS
        Timeouts: Har network call par timeout zaroori hai (connection timeout 2s, read timeout 5s).
                  Bina timeout ke ek slow service poore server ke worker threads block kar sakti hai.
        Retries : Sirf transient (503, network glitch) errors par retry karo.
                  Exponential Backoff + Jitter (random delay) use karo taaki saare
                  clients ek saath retry karke service ko dobara crush na karein.
        Circuit Breaker:
                  Agar downstream service lagatar fail ho rahi hai, toh turant calls
                  rok do (Open state) aur graceful fallback return karo.

    19. SQL INJECTION (SQLi)
        Samasya : User input ko string concatenation se SQL me daalna (`"WHERE id = " + input`).
        Solution: Parameterized Queries / Prepared Statements (`WHERE id = ?`).
                  Input ko data maana jaata hai, executable SQL syntax nahi.
        Rule    : ORM use karte waqt bhi raw queries (`DB::raw()`) me user input string
                  concatenate mat karo.

    20. HTTPS & TLS
        Kyun    : Data in transit ko encryption, integrity (tampering prevention), aur
                  authenticity (SSL certificate) deta hai.
        Flow    : Client Hello -> Server Hello + Certificate -> Key Exchange -> Symmetric Encrypted Traffic.
        Catch   : HTTPS packet sniffers se bachata hai, par SQL injection ya broken
                  authorization se nahi bachata — application layer security alag zimmedari hai.

4. BONUS 1: HOW THE 20 CONCEPTS WORK TOGETHER (E-COMMERCE FLOW)
------------------------------------------------------------
    User order place karta hai:
    1. Request     : Mobile/Web HTTPS se REST API par request bhejta hai (01, 02, 03, 20).
    2. Traffic     : Load Balancer healthy server instance par traffic bhejta hai (14, 15).
    3. Security    : Rate Limiting bot traffic rokti hai; AuthN/AuthZ token check karti hai (04, 05, 17).
    4. Cache       : Product details Redis cache se nikalte hain (13).
    5. Database    : Connection pool se connection le kar ACID transaction me stock
                     deduct hota hai aur order banta hai (07, 08, 09, 11, 19).
    6. Performance : Eager loading se N+1 query problem avoid hoti hai (12).
    7. Async Tasks : Message queue me event jata hai -> worker invoice banata hai
                     aur email bhejta hai (16).
    8. Resiliency  : Payment gateway call me timeout, retry backoff aur idempotency key
                     hoti hai (03, 18).

5. BONUS 2: 15 TOP BACKEND INTERVIEW QUESTIONS & ANSWERS
------------------------------------------------------------
    Q01: Browser me URL enter karne par kya hota hai?
    A01: DNS lookup -> TCP 3-way handshake -> TLS negotiation -> HTTP request ->
         Server routing/controllers -> DB queries -> HTTP response -> Browser rendering.

    Q02: REST aur GraphQL me kya farak hai?
    A02: REST me fixed endpoints aur fixed data structure hota hai (over-fetching/under-fetching).
         GraphQL me single endpoint par client exact fields query karta hai.

    Q03: PUT aur PATCH me kya farak hai?
    A03: PUT poore resource ko replace karta hai (idempotent); PATCH sirf specific
         fields update karta hai.

    Q04: Authentication vs Authorization?
    A04: AuthN verify karta hai user kaun hai; AuthZ check karta hai user ko kya permission hai.

    Q05: JWT kab aur Session kab?
    A05: Strict central logout/revocation chahiye toh Sessions (Redis). Microservices
         ya horizontal decoupled systems me short-lived JWT + refresh token.

    Q06: SQL vs NoSQL kab chunoge?
    A06: Strict relations, transactional integrity, multi-table joins = SQL. Unstructured
         documents, high-throughput key-value, caching = NoSQL.

    Q07: Index lagane se performance kaise badhti hai? Trade-off kya hai?
    A07: B-Tree se O(N) table scan O(log N) ho jaata hai. Trade-off: disk space leta
         hai aur INSERT/UPDATE/DELETE queries ko slow karta hai.

    Q08: ACID properties samjhao.
    A08: Atomicity (all or nothing), Consistency (rules intact), Isolation (transactions independent),
         Durability (committed data safe permanently).

    Q09: N+1 query problem kya hai aur kaise theek hoti hai?
    A09: 1 query collection ke liye + N queries related data ke liye. Fix: Eager loading ya SQL JOIN.

    Q10: Caching aur Indexing me farak?
    A10: Indexing database engine ke andar data jaldi dhoondhti hai; Caching computed
         result ko alag fast layer (RAM/Redis) me store kar leti hai.

    Q11: Million requests per second API kaise scale karoge?
    A11: Stateless app instances + Load Balancer, Redis caching, DB Read Replicas,
         Database Sharding, Async message queues, aur CDN for static assets.

    Q12: Message Queues kyun use karte hain?
    A12: Heavy work ko decouple karne, request latency kam karne, aur traffic spikes
         ko buffer karne ke liye.

    Q13: SQL Injection se kaise bachein?
    A13: Prepared Statements aur Parameterized Queries use karke; user input ko kabhi
         SQL string me concatenate na karein.

    Q14: Downstream third-party service fail ho jaaye toh kya karein?
    A14: Explicit timeouts, exponential backoff + jitter ke saath bounded retries,
         aur Circuit Breaker pattern.

    Q15: Duplicate payments hone se kaise rokein?
    A15: Idempotency Keys use karke, DB me unique transaction constraints laga kar,
         aur state-machine validation karke.

6. BONUS 3: PRACTICAL PROJECT BLUEPRINT – URL SHORTENER
------------------------------------------------------------
    Concept ko real project me implement karne ka architecture:

    Database Schema:
    - USERS      : id (PK), name, email, password_hash, created_at
    - URLS       : id (PK), user_id (FK), short_code (UNIQUE, INDEXED),
                   original_url, created_at, expires_at
    - URL_CLICKS : id (PK), url_id (FK), clicked_at, ip_address, referrer

    API Endpoints:
    - POST /api/auth/register
    - POST /api/auth/login
    - POST /api/urls               (Authenticated, Rate limited)
    - GET  /api/urls/{shortCode}   (Public redirect, Cache-aside Redis, 301/302)
    - GET  /api/urls/{shortCode}/stats (Analytics)
    - DELETE /api/urls/{id}        (Authorization: check user ownership)

    Concepts Covered:
    - Redis Cache  : Short-code -> Original URL map cache karo (99% reads DB tak na jaayein).
    - Rate Limit   : 10 URLs/min per user (abuse protection).
    - Background   : Click analytics logging message queue me push karo taaki redirect fast ho.
